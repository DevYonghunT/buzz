# SchoolX 2.0 개발 계획

## 1. 목표

SchoolX 2.0은 Buzz를 기반으로 다음 목표를 달성한다.

- Buzz가 이미 제공하는 협업 기능을 최대한 그대로 사용한다.
- 기존 SchoolX의 업무방 구조와 에이전트 운영 방식을 Buzz의 선택형 채널 템플릿과 권한 제한형 에이전트로 재구성한다.
- 사용자 화면은 한국어를 기본으로 제공하되 영어 폴백을 유지한다.
- Buzz에 없는 SchoolX 전용 기능은 첫 버전에 새로 만들지 않는다.
- upstream `block/buzz`의 개선 사항을 계속 받아올 수 있도록 변경 범위를 얇게 유지한다.

SchoolX 2.0의 제품 정의는 새로운 협업 엔진이 아니라 **한국어 교육·연구 조직을 위한 Buzz 운영 패키지**다. 핵심 가치는 한국어 업무 환경, 목적별 워크스페이스 템플릿, 출처가 명확한 협업 에이전트에서 만든다.

## 2. 제품 원칙

### 2.1 Buzz 네이티브 우선

기능 요구가 생기면 아래 순서로 해결한다.

1. Buzz의 기존 기능을 설정이나 템플릿으로 조합한다.
2. 기존 Buzz 기능에 작은 확장 포인트를 추가한다.
3. 그래도 해결되지 않는 경우에만 SchoolX 전용 기능을 별도 백로그로 검토한다.

### 2.2 프로토콜과 데이터 호환성 유지

- 채널, 메시지, 멤버십은 Buzz가 사용하는 Nostr 이벤트 구조를 유지한다.
- 별도의 SchoolX 전용 HTTP API나 데이터베이스 테이블을 우선 도입하지 않는다.
- 사용자 콘텐츠는 SchoolX 전용 포맷으로 잠그지 않는다.
- CLI와 에이전트가 기존 Buzz 채널에 동일하게 접근할 수 있어야 한다.

### 2.3 제품 변경과 upstream 변경 분리

- 제품명, 아이콘, 기본 언어, 초기 템플릿은 SchoolX 설정 계층에 모은다.
- Buzz 핵심 로직을 직접 복제하거나 대규모로 수정하지 않는다.
- upstream 동기화 시 충돌이 잦은 파일은 가능한 한 래퍼나 설정 파일로 분리한다.

브랜딩은 표시 문자열만 바꾸는 작업으로 취급하지 않는다. 앱 식별자, 데이터
디렉터리, 딥링크, 업데이트 채널, CLI가 읽는 로컬 파일 경로는 하나의 제품
호환성 계약으로 설계한다.

| 항목 | SchoolX 1차 원칙 | 반드시 검증할 호환성 |
|---|---|---|
| 표시 이름과 아이콘 | 제품 설정에서 SchoolX 값 사용 | 프로토콜 설명과 사용자 콘텐츠 속 `Buzz`는 자동 치환하지 않음 |
| 앱 식별자 | Buzz와 다른 식별자 사용 | 동시 설치, 업데이트, 제거 시 상대 제품 데이터에 쓰지 않음 |
| 데이터 디렉터리 | SchoolX 전용 디렉터리 사용 | 기존 Buzz 데이터는 명시적 가져오기 전에는 읽거나 이동하지 않음 |
| 새 딥링크 생성 | 최종 SchoolX 스킴 결정 후 제품 설정에서 생성 | 이미 저장된 `buzz://` 링크의 수신 정책과 Buzz↔SchoolX 동작을 별도 정의 |
| OS 딥링크 등록 | 한 스킴을 두 앱이 동시에 소유한다고 가정하지 않음 | 동시 설치 순서별 기본 핸들러와 실패 UX 검증 |
| 초대·연결·Nostr 바인딩 | 프로토콜 호환성이 필요한 경로는 기존 의미 유지 | `message`, `join`, `connect`, `add-community`, `nostr-bind`별 호환성 테스트 |
| CLI 로컬 템플릿 경로 | bundle identifier에서 파생하거나 명시적 인자로 전달 | `xyz.block.buzz.app` 하드코딩 제거 전 SchoolX CLI 완료로 간주하지 않음 |
| 업데이트와 서명 | SchoolX 전용 채널과 서명 주체 사용 | Buzz 업데이트가 SchoolX를 덮어쓰거나 그 반대가 되지 않음 |

딥링크 스킴을 변경하더라도 메시지에 이미 저장된 링크는 데이터 호환성의
일부다. 새 링크 생성 규칙, 과거 링크 수신 규칙, OS 등록 주체를 각각
결정하기 전에는 브랜딩 단계를 완료로 표시하지 않는다.

### 2.4 복제 대신 출처가 있는 공유

- 다른 업무방에 내용을 복사하거나 가져오기보다 원본 메시지와 스레드를 링크한다.
- 공유되는 요약에는 원본 채널, 작성자, 작성 시각, 원본 링크를 포함한다.
- 출처 링크는 접근 제어가 아니다. 링크를 붙였다는 이유만으로 비공개 내용을 더 넓은 채널에 요약해 게시하지 않는다.
- 여러 출처를 요약할 때 허용 독자 범위는 각 출처 채널 독자 집합의 교집합으로 계산한다.
- 요약 대상 채널의 현재 독자 집합이 허용 독자 교집합의 부분집합일 때만 자동 초안을 만들 수 있다.
- 비공개 출처를 포함한 교차 채널 결과는 1차 버전에서 자동 게시하지 않는다. 사람이 내용을 검토해 공개 가능한 새 문서로 명시적으로 승인하거나, 본문 없이 권한 확인이 가능한 원본 링크만 공유한다.
- 출처 채널의 멤버가 아닌 사용자에게는 채널 제목, 미리보기, 요약도 노출하지 않는다.
- 회의방은 다른 업무방의 사본 저장소가 아니라, 출처 링크를 중심으로 논의하고 결정하는 공간으로 사용한다.

여기서 private 채널의 기밀성 독자 집합은 현재 active member 집합이고,
open 채널의 기밀성 독자 집합은 해당 커뮤니티의 모든 인증 사용자다. 다만
검증된 NIP-OA 관리형 에이전트는 open 여부와 무관하게 active member인
채널만 읽고 쓸 수 있도록 서버가 별도로 제한한다. 대상이 open이면 모든
source가 open인 경우를 제외하고 private-source 본문을 게시할 수 없다.
생성 시작 때 계산한 결과를 재사용하지 않고 실제 게시 직전에 source와
target membership 및 에이전트 분류를 다시 확인하며, 중간에 권한이 바뀌면
게시를 실패시킨다.

현재 `buzz-core::audience`는 source 교집합과 target 부분집합을 검사하는
zero-I/O 정책 primitive다. 요약·보고서 이벤트의 생성·게시 경로에 이
primitive와 최신 DB snapshot 조회가 연결되기 전에는 end-to-end 자동 게시
보안이 구현됐다고 간주하지 않는다.

대상 채널의 멤버가 나중에 늘어나면 과거 메시지도 새 멤버에게 보일 수 있다.
따라서 비공개 출처의 내용을 다른 채널에 영구 게시하는 행위는 단순 전달이
아니라 **공개 범위 변경**으로 취급한다. 현재 멤버 집합 검사만으로 미래
누출까지 해결된다고 주장하지 않으며, 자동화는 링크 중심으로 제한한다.

### 2.5 자동 영구 기억 대신 검증된 지식

정보는 다음 세 단계로 다룬다.

1. **대화**: 검색 가능한 원본이지만 공식 지식은 아니다.
2. **AI 요약**: 출처를 포함한 임시 결과이며 언제든 원본과 대조할 수 있다.
3. **검증된 캔버스**: 사람이 확인해 공식 지식으로 승격한 내용이다.

AI가 모든 대화를 자동으로 영구 기억하게 하지 않는다. 장기적으로 재사용할 지식은 사용자의 명시적 승격을 거쳐 캔버스에 기록한다.

1차 버전에서 이 세 단계는 새 데이터 모델이 아니라 다음 운영 계약이다.

- AI 결과는 메시지 또는 스레드에 `AI 초안`임을 표시하고 출처 링크를 포함한다.
- 에이전트는 공식 캔버스를 직접 덮어쓰지 않는다.
- 사용자가 초안을 검토·수정한 뒤 수동으로 캔버스에 반영하고, 캔버스에는 검토자와 원본 링크를 남긴다.
- 캔버스의 일반 편집 이력과 감사 로그를 사용하며, 별도의 SchoolX 승인 상태나 자동 승격 이벤트를 1차 버전에 만들지 않는다.

별도 상태 전이, 승인 대기열, 자동 롤백이 필요하다는 파일럿 증거가 생기면
그때 새 기능 후보로 설계한다. 그 전에는 “화면의 상태 배지”가 서버가
강제하는 검증 상태인 것처럼 표현하지 않는다.

### 2.6 최소 권한과 요청 기반 자동화

- 코디네이터는 모든 채널을 기본 감시하지 않는다.
- 원본 Buzz의 `open` 채널은 멤버가 아닌 인증 사용자와 에이전트도 읽고 쓸 수 있었다. SchoolX foundation은 사람에게는 이 의미를 유지하되, 검증되거나 영속 분류된 NIP-OA 관리형 에이전트에는 open 채널도 active membership을 요구한다.
- 제한이 필요한 SchoolX 업무방과 메인 회의방은 1차 버전에서 `private`를 기본값으로 사용한다.
- ACP 구독 allowlist는 불필요한 자동 구독을 줄이는 운영 설정일 뿐 보안 경계로 간주하지 않는다.
- 에이전트가 가진 동일 자격증명으로 CLI, HTTP bridge, WebSocket REQ/COUNT/EVENT를 사용해도 동일한 채널 제한이 적용되어야 한다.
- NIP-OA 소유자 매핑은 최초 검증 후 community-scoped `users.agent_owner_pubkey`에 영속화하며, 이후 요청에서 auth tag를 생략해도 인간의 open-channel 의미로 되돌아가면 안 된다.
- SchoolX 배포는 relay membership을 요구하고 NIP-OA delegation을 명시적으로 활성화한다. open relay에서 아직 영속 분류되지 않은 새 키는 사람이 아닌 에이전트임을 서버가 추론할 수 없으므로 같은 보안 보장을 주장하지 않는다.
- 다른 채널로 내용을 게시하거나 외부 도구를 실행하는 작업은 사용자의 요청 또는 확인이 있어야 한다.
- 정기 요약은 관리자가 활성화한 채널과 시간 범위에 대해서만 실행한다.
- 결과에는 근거 링크와 실패 상태가 반드시 표시되어야 한다.
- 현재 Blossom 미디어 경로는 메시지의 `h` 태그와 같은 channel ACL을 제공한다고 가정하지 않는다. 민감 파일의 저장·공유 정책이 별도로 검증되기 전에는 private 채널 첨부만으로 파일 본문까지 격리됐다고 표현하지 않는다.

현재 Buzz workflow의 approval gate(WF-08)는 구현되지 않아 승인 단계에
도달한 실행이 실패한다. 따라서 WF-08이 승인·거절·만료·재시작까지
구현되고 검증되기 전에는 “사용자 확인형 자동 게시”를 제공한다고
표현하지 않는다. 1차 안전 모드는 에이전트가 허용된 private 채널에
초안을 만들고, 사용자가 일반 Buzz UI에서 수동으로 공유하는 방식이다.

### 2.7 고정 구조 대신 선택형 시작 템플릿

- 기존 SchoolX 업무방은 필수 데이터 구조가 아니라 선택 가능한 시작 템플릿으로 제공한다.
- 관리자는 필요한 업무방과 에이전트만 선택할 수 있다.
- 템플릿 적용 후에도 일반 Buzz 채널처럼 이름, 멤버, 에이전트, 운영 방식을 변경할 수 있다.
- 사용하지 않는 업무방과 에이전트를 자동으로 생성하지 않는다.

### 2.8 목표 구조

```text
SchoolX 제품 계층
├── 브랜드와 배포 설정
├── 한국어·영어 번역 카탈로그
├── 교육·연구 조직용 워크스페이스 템플릿
├── 페르소나와 에이전트 운영 정책
└── 캔버스·포럼·워크플로 운영 예제
              │
              ▼
Buzz 애플리케이션 계층
├── 채널·멤버십·메시지·검색
├── 에이전트·페르소나·팀
├── 캔버스·포럼·알림·워크플로
└── Huddle·파일·감사
              │
              ▼
Nostr 이벤트와 Buzz 인프라
```

SchoolX 계층은 Buzz의 공개된 기능과 일반화된 확장 지점을 사용한다. Buzz 핵심 계층에는 SchoolX 업무방 이름이나 전용 비즈니스 규칙을 넣지 않으며, 핵심 변경이 필요하면 다른 Buzz 배포에서도 사용할 수 있는 일반 기능으로 구현한다.

## 3. 1차 버전 범위

### 포함

- SchoolX 2.0 브랜딩
- 데스크톱 앱 핵심 화면 한국어화
- 한국어 입력기(IME), 검색, 날짜 및 시간 표시 검증
- 필요한 SchoolX 업무방을 선택해 생성하는 워크스페이스 템플릿
- 업무방별 재사용 가능 페르소나와 선택형 관리형 AI 에이전트
- 허용된 private 채널만 요청 기반으로 종합하는 회의방 코디네이터
- 메시지, 스레드, 반응, 검색, 파일, 캔버스, 포럼, 알림 기능
- Buzz Huddle을 이용한 실시간 음성 회의
- Buzz 워크플로를 이용한 같은 private 채널의 출처 기반 반복 요약 초안
- private 채널 권한과 멤버십을 이용한 기본 접근 제어
- 데스크톱 패키징과 내부 시험 배포

### 제외

- 기존 SchoolX 데이터의 자동 마이그레이션
- `shared_items`, `meeting_imports`와 같은 구조화된 공유·가져오기 모델
- 별도 의사결정 테이블과 태스크 관리 데이터 모델
- 검토 대기열이 있는 업무방별 도메인 메모리
- 파일 버전 관리와 SchoolX 전용 파일 ACL
- Google OAuth와 이메일 허용 목록
- Google Meet 및 Zoom 연동
- Huddle 카메라 영상과 화면 공유
- 기존 SchoolX와 완전히 동일한 관리자 대시보드
- 모바일과 웹의 전체 한국어화

제외 기능은 삭제하는 것이 아니라, 실제 사용 과정에서 Buzz 네이티브 기능만으로 부족한지 확인한 뒤 후속 버전에서 판단한다. “익숙했던 기능”이라는 이유만으로 복원하지 않고, 파일럿에서 반복적으로 해결되지 않은 사용자 문제가 확인된 경우에만 구현 후보가 된다.

## 4. 한글화 가능성 및 전략

### 4.1 조사 결과

한글화는 가능하다. 비교 기준인 원본 Buzz snapshot에는 앱 전체를 위한
다국어 프레임워크가 없고, 데스크톱·웹·모바일 화면에 영어 문구가 직접
작성되어 있다. SchoolX foundation snapshot에는 데스크톱용 초기 runtime만
추가된 상태다.

- 데스크톱은 React/TypeScript이므로 런타임 언어 전환과 번역 카탈로그를 추가할 수 있다.
- 메시지 입력기는 웹 편집기 기반이므로 한글 입력이 가능하지만, 조합 중 Enter 처리와 멘션·자동완성은 별도 회귀 테스트가 필요하다.
- 날짜 표시는 상당 부분 운영체제 로케일을 따르지만, 표시 형식을 현재 앱 언어의 `ko-KR` 또는 영어 형식으로 통일해야 한다.
- 현재 기본 글꼴인 Inter에는 한글 글리프가 충분하지 않아 시스템 글꼴로 폴백된다. 명시적인 한국어 시스템 글꼴 스택이 필요하다.
- 모바일에는 `intl` 패키지가 있지만 Flutter 로컬라이제이션 설정은 아직 없다.

### 4.2 적용 원칙

- 1차 대상은 데스크톱 앱으로 제한한다.
- 기본 언어는 한국어, 폴백 언어는 영어로 한다.
- 사용자가 설정에서 한국어와 영어를 바꿀 수 있게 한다.
- 프로토콜 이름, CLI 명령, 이벤트 kind, 로그 필드는 번역하지 않는다.
- 사용자에게 노출되는 Rust/Tauri 오류는 점진적으로 안정된 오류 코드에 매핑해 번역한다.
- 개발 문서와 코드 식별자는 영어를 유지한다.

1차 버전의 초기 언어 결정표는 다음과 같다.

| 저장된 선택 | 운영체제 언어 | 초기 UI 언어 | 비고 |
|---|---|---|---|
| `ko` | 무관 | 한국어 | 저장된 선택 우선 |
| `en` | 무관 | 영어 | 저장된 선택 우선 |
| 없음 | 지원되는 한국어 태그 | 한국어 | `ko`, `ko-KR`, `ko-Hang-KR` 등 정규화 |
| 없음 | 지원되는 영어 태그 | 영어 | `en`, `en-US`, `en_GB` 등 정규화 |
| 없음 | 미지원 또는 조회 불가 | 한국어 | SchoolX 제품 기본값 |
| 손상된 값 또는 저장소 접근 실패 | 지원되는 OS 언어 | OS 언어 또는 한국어 | 앱 시작과 세션 내 언어 전환을 막지 않음 |

초기 언어는 **저장된 지원 언어 → 지원되는 운영체제 언어 → 한국어** 순서로
결정한다. 날짜·시간·숫자 형식도 현재 앱 언어에 맞춰 `ko-KR` 또는 영어
형식으로 표시한다. 이 우선순위를 바꾸려면 표와 단위·E2E 회귀 테스트를
같이 갱신한다.

### 4.3 권장 구현

데스크톱에 `i18next`와 `react-i18next`를 사용한다. 현재 foundation은
`locales/en.ts`, `locales/ko.ts`의 단일 `translation` namespace로
시작했으며, 이것만으로 Phase 2 전체가 완료된 것은 아니다. 대량 문자열
추출 전에 기능별 namespace로 전환하거나 단일 카탈로그를 유지할 근거를
결정한다. 병렬 작업과 upstream 충돌을 줄이기 위해 기본 선택은 기능별
namespace다.

목표 구조:

```text
desktop/src/shared/i18n/
├── index.ts
├── locale.ts
└── locales/
    ├── en/
    │   ├── common.ts
    │   ├── channels.ts
    │   ├── agents.ts
    │   └── settings.ts
    └── ko/
        ├── common.ts
        ├── channels.ts
        ├── agents.ts
        └── settings.ts
```

영어 catalog를 타입의 기준으로 삼아 코드에서 존재하지 않는 키를 사용할 수
없게 한다. 한·영 key 집합 일치 검사는 유지하되, 양쪽 catalog에서 같은
키가 동시에 빠지는 경우도 잡도록 실제 `t()` 사용 키 또는 typed resource를
검증한다. 한국어 키가 의도적으로 빠진 fixture에서 영어 문구가 표시되는
fallback 테스트도 둔다.

번역은 한 번에 모든 파일을 바꾸지 않고 사용자 여정 순서로 진행한다.

1. 앱 셸, 로그인과 온보딩
2. 채널 생성·참여·멤버 관리
3. 메시지·스레드·검색·파일
4. 에이전트·페르소나·팀
5. 캔버스·포럼·알림
6. Huddle·워크플로
7. 설정·오류·빈 상태

### 4.4 한글화 완료 기준

- 새 사용자가 영어 화면 없이 로그인하고 SchoolX 워크스페이스에 들어갈 수 있다.
- 채널 생성부터 메시지, 파일 공유, 에이전트 호출까지 핵심 흐름이 한국어로 표시된다.
- 한글 자모가 중복되거나 분리되지 않는다.
- 조합 중 Enter가 메시지를 잘못 전송하지 않는다.
- 한글 채널명, 한글 파일명, 한글 검색어가 정상 동작한다.
- 번역 키가 누락되면 앱이 깨지지 않고 영어가 표시된다.
- `ko-KR`과 영어 환경에서 레이아웃이 잘리거나 겹치지 않는다.
- localStorage가 비어 있는 실제 앱 부팅에서 지원되는 `en-US`는 영어,
  미지원 `ja-JP`는 한국어가 표시되고, 한국어와 영어 양방향 전환 및
  새로고침 유지가 E2E로 검증된다.

## 5. SchoolX 기능을 Buzz로 구성하는 방법

| SchoolX 사용 목적 | SchoolX 2.0에서 사용할 Buzz 기능 | 1차 구현 방식 |
|---|---|---|
| 부서·업무방 | NIP-29 채널과 멤버십 | 관리자가 선택한 채널만 워크스페이스 템플릿으로 생성 |
| 업무방 전문 AI | 관리형 에이전트, 페르소나, 팀 | 페르소나는 제공하되 자주 쓰는 방만 관리형 에이전트를 활성화 |
| 메인 회의방 | 채널, 스레드, Huddle | 전체 멤버가 참여하는 private 회의 채널과 실시간 음성 Huddle 사용 |
| 총괄 조정 AI | private 채널 멤버십과 제한된 ACP 구독을 가진 관리형 에이전트 | 허용된 private 채널만 요청 시 검색·요약하고 자동 교차 게시 금지 |
| 회의 결과 정리 | 스레드 요약, 채널 요약, 캔버스 | 출처가 있는 임시 요약을 사람이 확인한 뒤 캔버스에 승격 |
| 부서 간 공유 | 메시지 링크, 멘션, 캔버스, 포럼 | 접근 가능한 원본 링크를 공유하고, 본문 요약은 사람이 공개 범위를 확정한 경우만 공유 |
| 의사결정 | 포럼 글, 스레드, 반응, 캔버스 | 포럼에서 합의한 뒤 검증된 결과만 결정 캔버스에 기록 |
| 할 일 | 알림, 워크플로, 캔버스 체크리스트 | 담당자 멘션, 기한 알림, 반복 워크플로 사용 |
| 자료 공유 | Buzz 파일 업로드와 미디어 | 채널이나 스레드에 파일을 올려 대화 맥락과 결합 |
| 지식 축적 | 검색, 출처 기반 요약, 캔버스 | 대화 → AI 요약 → 사람이 검증한 캔버스의 3단계로 관리 |
| 정기 보고 | 워크플로 YAML과 에이전트 | workflow가 같은 채널에서 코디네이터를 멘션해 초안을 요청하고 사용자가 검토한 뒤 공유 |
| 접근 권한 | private 채널 역할과 멤버십 | `open`은 커뮤니티 전체 접근임을 표시하고 민감 업무방은 private로 제한 |
| 음성 회의 | Buzz Huddle | 1차 버전은 내장 음성 Huddle을 사용하고 카메라·화면 공유는 제공하지 않음 |
| 변경 이력 | 이벤트 로그와 감사 체인 | Buzz의 이벤트 및 감사 기능을 그대로 사용 |

## 6. 기본 워크스페이스 설계

기존 SchoolX의 활성 업무방을 선택형 템플릿으로 제공한다. 설치 시 채널이나 에이전트를 강제로 생성하지 않고, 관리자가 “SchoolX 기본 워크스페이스” 미리보기에서 필요한 항목만 선택한다.

| 안정 키 | 표시 이름 | 기본 역할 | 기본 공개 범위 | 제공 페르소나 | 초기 활성화 |
|---|---|---|---|---|---|
| `meeting` | 메인 회의방 | 전사 회의, 종합 보고, 음성 Huddle | private | SchoolX 코디네이터 | 파일럿에서 선택 |
| `finance` | 재무 | 예산, 지출, 정산 | private | 재무 담당 | 비활성 |
| `planning` | 기획 | 사업 기획, 일정, 제안 | private | 기획 담당 | 파일럿에서 선택 |
| `external` | 대외협력 | 기관 협력, 공문, 대외 일정 | private | 대외협력 담당 | 비활성 |
| `development` | 개발 | 제품 개발, 기술 검토 | private | 개발 담당 | 비활성 |
| `research` | 연구 | 조사, 자료 분석, 연구 기록 | private | 연구 담당 | 비활성 |
| `promotion` | 홍보 | 콘텐츠, 보도, 홍보 일정 | private | 홍보 담당 | 비활성 |
| `province_research` | 경기도교육연구회 | 지역 연구회 협업 | private | 연구회 담당 | 비활성 |
| `science_museum` | 과학관 AI교육 연구회 | AI 교육 공동 연구 | private | AI교육 연구 담당 | 비활성 |
| `gwangju_hanam_research` | 광주하남교육연구회 | 지역 연구회 협업 | private | 연구회 담당 | 비활성 |

비활성 상태였던 `city_research`는 기본 템플릿에서 제외한다.

관리자는 적용 전에 공개 범위를 바꿀 수 있지만, `open`을 선택하면
“모든 인증 사용자가 멤버십 없이 읽고 쓸 수 있음”과 “관리형 에이전트는
명시적으로 추가된 경우만 접근 가능함”을 미리보기와 확인 화면에 함께
명시한다. private 채널의 이름이나 존재 자체가 비멤버에게 노출되지
않는지도 권한 테스트에 포함한다.

### 버전이 있는 내장 catalog

SchoolX 기본 워크스페이스는 사용자가 만든 단일 채널 템플릿 파일과 별도로
배포되는 읽기 전용 catalog다.

- catalog에는 안정적인 `catalog_id`, 증가하는 `catalog_version`, 각 항목의 `item_key`를 둔다.
- 앱에 포함된 built-in 정의와 사용자가 복사·수정한 템플릿을 별도 레코드로 유지한다.
- 업그레이드 시 built-in 정의는 새 버전으로 교체하되 사용자 복사본과 이미 적용한 채널 설정을 자동 덮어쓰지 않는다.
- catalog에서 제거된 항목은 새 적용 화면에서 숨기되 기존 채널을 삭제하지 않는다.
- fresh install, catalog upgrade, 사용자 수정본, 제거된 item을 각각 snapshot과 E2E로 검증한다.
- SchoolX 앱 식별자 변경 뒤 CLI가 같은 catalog를 읽는 경로를 제품 설정에서 파생한다.

기존 template store가 없을 때 빈 배열을 반환하고 UI 생성 템플릿이
`is_builtin=false`인 현재 동작만으로는 내장 catalog가 제공된 것으로
간주하지 않는다.

### 채널 기본 구성

각 업무방 템플릿에는 다음 항목을 포함한다.

- 안정적인 catalog item key와 버전
- 한글 채널 이름과 설명
- 명시적인 `private`/`open` 공개 범위
- 채널의 목적과 운영 규칙을 담은 시작 캔버스
- 업무방에 맞는 에이전트 페르소나
- 관리형 에이전트 활성화 여부 선택
- 반복 업무를 위한 선택형 워크플로 예제
- 결정 기록, 주간 요약, 할 일 기록용 캔버스 섹션
- 새 멤버가 따라 할 수 있는 한국어 시작 안내

### provenance, 재적용, 부분 실패

현재 채널 생성은 매번 임의 UUID를 만들고 template ID를 채널에 남기지
않으므로 이름 비교만으로 재적용을 구현하지 않는다. 구현 전에 다음 논리
필드를 relay에서 다시 확인 가능한 일반화된 metadata 또는 manifest로
보존한다.

- `catalog_id`
- `catalog_version`
- `item_key`
- 적용으로 생성된 channel ID
- 선택한 persona/agent/workflow 항목과 적용 상태

전용 SchoolX 데이터베이스 테이블을 우선 만들지는 않되, 로컬 파일만 잃으면
provenance가 사라지는 설계도 허용하지 않는다. 구체적인 Nostr 표현은
다른 Buzz 배포에서도 재사용 가능한 workspace-template manifest로
설계하고 구현 전에 프로토콜 리뷰를 받는다.

전체 적용을 단일 원자적 트랜잭션으로 가장하지 않고 idempotent saga로
처리한다.

1. preflight에서 생성, 재사용, 충돌, 건너뜀, 권한 부족을 미리 보여준다.
2. 각 단계는 stable key와 기존 manifest를 확인한 뒤 한 번만 효과를 낸다.
3. 채널 생성, 캔버스, 멤버, 에이전트, workflow 단계별 성공·실패를 기록한다.
4. 재시도는 실패하거나 미완료인 단계만 실행한다.
5. 사용자가 rename한 채널은 channel ID와 provenance로 추적하고 원래 이름으로 되돌리지 않는다.
6. 사용자가 삭제한 채널은 자동 재생성하지 않고 명시적으로 선택하게 한다.
7. 동명 채널에 provenance가 없으면 자동 채택하지 않고 충돌 해결을 요청한다.
8. 보상 작업은 이번 실행에서 새로 만든 리소스만 대상으로 하며 기존 사용자 데이터는 자동 삭제하지 않는다.

완료 기준은 “중복이 무한히 늘지 않음”이 아니라, 같은 선택으로 두 번
적용했을 때 두 번째 preflight가 변경 없음이고 channel/agent 수가 정확히
같은 것이다. 각 단계에서 의도적으로 실패시킨 뒤 재시도해도 같은 결과에
도달해야 한다.

### 에이전트 권한 원칙

- 업무방 에이전트는 업무방의 active member로만 추가하고, ACP 구독 범위도 같은 채널로 제한한다.
- 서버는 검증되거나 영속 분류된 NIP-OA 에이전트에 대해 private/open 모두 active membership을 강제한다. ACP allowlist나 프롬프트를 이 강제의 근거로 사용하지 않는다.
- 코디네이터는 사용자가 명시적으로 허용한 업무방에만 참여한다.
- 코디네이터는 호출 또는 활성화된 일정이 없으면 채널을 자동 요약하지 않는다.
- 비공개 채널의 정보를 다른 채널에 자동 복사하지 않는다.
- 채널 간 초안은 출처 audience 교집합과 대상 채널 audience를 검사하고, 출처 메시지 링크와 대상 채널을 명시한다.
- 에이전트 메모리는 공식 지식으로 간주하지 않으며, 캔버스 승격은 사람이 결정한다.
- WF-08이 구현되기 전에는 외부 도구 호출이나 게시 전 승인이 필요한 업무를 자동 실행하지 않는다.

## 7. 단계별 개발 계획

### Phase 0 — 기준선과 개발 운영

목표: 원본 Buzz가 정상 동작하는 기준선을 만들고 upstream 추적 방식을 고정한다.

작업:

- `origin`은 `DevYonghunT/buzz`, `upstream`은 `block/buzz`로 유지
- SchoolX 개발 브랜치는 `codex/schoolx-2-foundation`에서 시작
- 변경 전 parent SHA와 구현 snapshot SHA를 함께 기록
- Hermit, Node, pnpm, Rust 버전과 정확한 검증 명령, 실행 시각, 통과·실패 수를 기록
- 변경 전 detached worktree와 현재 브랜치에서 같은 데스크톱 빌드·테스트·린트를 실행
- SchoolX 변경 사항의 디렉터리와 네이밍 규칙 확정
- Apache-2.0 원문, NOTICE, 서드파티 라이선스 보존 확인
- upstream 반영 절차 문서화
- 결과를 [`BASELINE.md`](BASELINE.md)에 보존하고 실행하지 않은 항목은 `미검증`으로 표시

완료 기준:

- [`BASELINE.md`](BASELINE.md)에 원본과 현재 snapshot의 같은 명령 결과가 모두 있다.
- 기존 실패와 새 변경으로 발생한 실패를 명령, test name, commit 기준으로 구분할 수 있다.
- 원본 Buzz 데스크톱을 로컬에서 실행할 수 있고 upstream fetch와 병합 절차를 재현할 수 있다.
- 미검증 항목이 남아 있으면 Phase 0이나 Phase 1 전체를 완료로 표시하지 않는다.

### Phase 1 — 보안과 호환성 설계 게이트

목표: 템플릿이나 에이전트를 만들기 전에 Buzz의 실제 접근 의미와
SchoolX 제품 경계를 검증 가능한 계약으로 고정한다.

작업:

- open 채널은 인증 사용자인 비멤버가 읽고 쓸 수 있지만 관리형 에이전트는 active membership이 필요하다는 principal별 의미를 threat model에 기록
- private 채널 멤버십, ACP 구독 allowlist, 일반 NIP-42 자격증명, scoped credential의 차이 정리
- REQ, COUNT, search, HTTP bridge, EVENT, Buzz CLI별 접근 매트릭스 테스트 작성
- 멤버 추가·제거와 cache 기간 전후의 접근 회귀 테스트 작성
- 여러 source의 audience 교집합과 target audience 부분집합 검사 규칙 정의
- 초안 생성과 실제 게시 사이의 membership 변경 시 재검사·실패 규칙 정의
- private source의 자동 교차 게시를 금지하고 수동 공개 범위 변경 절차 정의
- WF-08의 미구현 상태와 1차 manual-review fallback 확정
- 브랜드·앱 식별자·데이터 디렉터리·딥링크·CLI 경로 호환성 표의 값 확정
- Huddle의 1차 범위를 음성으로 고정하고 영상·화면 공유를 제외

완료 기준:

- 비멤버 에이전트가 private 채널의 존재, 제목, 메시지, 검색 결과, 요약을 얻거나 쓰지 못한다.
- 같은 에이전트가 ACP뿐 아니라 직접 CLI/HTTP/WebSocket을 사용해도 private 경계를 우회하지 못한다.
- open 채널을 선택하면 전체 인증 사용자 접근과 관리형 에이전트의 명시적
  멤버십 규칙이 UI와 문서에 표시된다.
- 허용 audience 교집합보다 넓은 target에는 본문 요약이 생성·게시되지 않는다.
- 생성 뒤 게시 전에 member가 바뀌는 race와 예약 실행에서도 같은 audience 검사가 적용된다.
- WF-08이 없을 때 자동 승인 모드가 노출되지 않고 수동 공유만 가능하다.
- Buzz와 SchoolX의 동시 설치, 과거 링크 처리, 로컬 데이터 경로에 대해 테스트 가능한 결정표가 있다.

이 단계는 이후 모든 agent-bearing template과 교차 채널 시나리오의 선행
조건이다. 현재 구현된 i18n foundation은 이 게이트를 대신하지 않는다.

### Phase 2 — 한글화 기반과 제품 브랜딩

목표: 보안 계약을 유지하면서 첫 사용자 여정을 한국어 SchoolX 앱으로
완성한다.

현재 상태: `a3e1ca4f`의 초기 runtime 위에 현재 작업트리에서 locale
우선순위, 실제 namespace, typed key, 공용 `Intl` formatter, 접근 가능한
언어 선택 UI와 fresh-install E2E를 보강했다. 대표 검색 날짜와 숫자 표시는
runtime locale을 따른다. 이는 **i18n 구조 foundation 완료**이며 핵심 화면
번역과 브랜딩을 포함한 Phase 2 완료가 아니다.

작업:

- 초기 언어 결정표와 E2E를 유지하고 저장소 차단 회귀를 보존
- 영어 missing-key fallback E2E 추가
- namespace별 물리 파일 분리는 catalog 규모가 커질 때 수행
- 앱 셸, 로그인, 온보딩, 채널 목록, 메시지 화면 우선 번역
- 한국어 IME 조합 중 Enter, 멘션, 자동완성 회귀 테스트
- 날짜·시간·숫자 표시를 현재 앱 언어에 맞게 통일
- 제품 설정 계층을 먼저 만들고 표시명, 아이콘, 앱 식별자, 딥링크 생성을 연결
- “Buzz”가 프로토콜·기술명인지 표시 제품명인지 구분해 문자열 추출
- SchoolX bundle ID에 맞춰 CLI template 경로와 update/signing 설정 분리

결정이 필요한 값:

- 최종 제품 표시명
- macOS/Windows/Linux 앱 식별자와 데이터 디렉터리
- 새로 생성할 딥링크 스킴과 과거 `buzz://` 수신 정책
- 아이콘과 색상
- 업데이트 서버와 배포 서명 주체

완료 기준:

- 한국어 환경에서 설치, 실행, 로그인, 채널 입장, 메시지 전송이 가능하다.
- 영어를 선택하면 핵심 사용자 여정 전체가 영어 UI로 돌아간다.
- fresh-install, 저장소 실패, 한·영 양방향 전환, missing-key fallback E2E가 통과한다.
- 한글 IME와 한글 검색 핵심 회귀 테스트가 통과한다.
- Buzz와 SchoolX를 함께 설치해도 데이터, 딥링크, 업데이트가 충돌하지 않는다.
- upstream 변경과 제품 브랜딩 변경이 가능한 한 분리되어 있다.

### Phase 3 — versioned 워크스페이스 catalog와 채널 적용

목표: 에이전트 없이도 빈 SchoolX 설치에 선택한 private 업무방을
재현 가능하고 복구 가능한 방식으로 구성한다.

작업:

- `catalog_id`, `catalog_version`, stable `item_key`가 있는 built-in catalog 정의
- 메인 회의방과 기획방만 포함한 최소 파일럿 preset부터 제공
- channel, canvas, membership 단계의 relay-visible provenance 설계
- preflight와 idempotent saga 실행기, 단계별 result ledger 구현
- rename, delete, 동명 충돌, 부분 실패, 재시도, catalog upgrade 규칙 구현
- 적용 미리보기에서 공개 범위와 open 의미를 명시
- 템플릿이 없던 fresh install에 built-in catalog를 seed
- 채널 생성과 캔버스 적용까지만 먼저 검증하고 agent provisioning은 Phase 4로 분리

완료 기준:

- 관리자가 선택한 private 업무방만 생성되고 선택하지 않은 항목은 생성되지 않는다.
- 같은 catalog version과 선택을 두 번 적용하면 두 번째 실행은 변경 없음이다.
- 이름을 바꿔도 channel ID와 provenance로 같은 항목을 추적한다.
- provenance 없는 동명 채널은 자동 채택하지 않는다.
- 각 단계 실패 후 재시도해도 중복 없이 최종 desired state에 도달한다.
- catalog upgrade가 사용자 수정 채널이나 사용자 template copy를 덮어쓰거나 삭제하지 않는다.
- 성공, 실패, 건너뜀, 사용자 조치 필요 상태가 UI와 machine-readable 결과에 모두 표시된다.

### Phase 4 — 에이전트 운영과 네이티브 협업 흐름

목표: Phase 1의 보안 계약 위에서 필요한 private 업무방에만 전문
에이전트를 활성화하고, 새 SchoolX 데이터 모델 없이 초안→검토→캔버스
흐름을 검증한다.

대표 시나리오:

1. private 기획방에서 안건을 포럼 글로 작성하고 자료를 첨부한다.
2. 토론은 스레드로 유지한다.
3. 기획방 에이전트가 같은 채널에 출처가 있는 `AI 초안`을 만든다.
4. 사람이 초안을 확인·수정하고 결정 캔버스에 수동 반영한다.
5. 캔버스에는 검토자, 원본 안건, 토론 스레드 링크를 유지한다.
6. 메인 회의방에는 기본적으로 원문 링크만 공유한다.
7. 원문 내용을 포함한 교차 채널 게시가 필요하면 audience 검사 후 사용자가 공개 가능한 내용으로 직접 확정한다.

작업:

- 업무방별 시스템 프롬프트, 역할, 금지 사항 정의
- 페르소나 호출과 상주 관리형 에이전트의 사용 기준 정의
- 관리형 에이전트는 catalog에서 기본 비활성 상태로 제공
- agent provisioning도 stable item key와 saga ledger에 포함
- 에이전트의 ACP 구독뿐 아니라 Buzz CLI/HTTP/WebSocket 접근 범위 검증
- 메인 회의방 코디네이터를 관리자가 허용한 private 채널에만 멤버로 추가
- 사용자 호출이 있을 때만 코디네이터가 보고서 초안을 생성
- source provenance와 audience 교집합을 machine-readable 결과에 포함
- AI 초안 라벨과 수동 canvas 반영 운영 흐름 구현
- 실패, timeout, 권한 부족, source 접근 상실을 추측 대신 사용자 상태로 표시
- 한글 파일명 업로드·다운로드·검색과 포럼·스레드·반응 흐름 검증

완료 기준:

- 업무방 에이전트가 다른 private 업무방의 존재, 제목, 메시지, 검색 결과를 얻거나 쓰지 못한다.
- 직접 CLI/HTTP/WebSocket을 사용해도 같은 결과이며 ACP allowlist만 통과 근거로 사용하지 않는다.
- 비활성 에이전트가 백그라운드에서 호출되거나 비용을 발생시키지 않는다.
- 모든 AI 초안에서 허용된 사용자는 근거 메시지로 이동할 수 있다.
- audience 교집합 밖의 target에는 private-source 요약 본문이 만들어지거나 게시되지 않는다.
- 자동 교차 게시 없이 사용자가 원문 링크, 초안, 검증된 캔버스를 구분해 검토·공유할 수 있다.
- 에이전트가 공식 캔버스를 자동으로 덮어쓰지 않는다.
- 재적용과 부분 실패 후에도 같은 persona의 관리형 에이전트가 중복 생성되지 않는다.

### Phase 5 — 회의와 자동화

목표: 외부 회의·자동화 제품 없이 Buzz 내장 기능의 실사용 가능성을 검증한다.

작업:

- 메인 회의방에서 음성 Huddle 생성·참여·종료 흐름 한국어화
- 회의 스레드 요약을 캔버스에 반영하는 운영 흐름 작성
- 관리자가 선택한 **같은 private 채널**에서 코디네이터를 멘션해 일간·주간 초안을 요청하는 workflow 예제 추가
- workflow action에 네이티브 agent invocation이 없으므로 `SendMessage`와 멘션의 실제 연결을 명세하고 테스트
- private source의 새 안건은 meeting 채널에 본문을 복사하지 않고 접근 제어된 링크 중심으로 공유
- WF-08 구현 전에는 workflow가 초안까지만 만들고 사용자가 수동 게시
- WF-08을 도입할 경우 approve, reject, timeout, restart, 중복 승인, 권한 취소를 먼저 구현·검증
- workflow 실패는 Workflows 화면과 요청 채널의 사용자 가시 상태 중 어디에 나타나는지 명시하고 조용한 누락 금지
- 자동화 비활성화와 실행 중 취소의 의미를 정의

완료 기준:

- 팀이 카메라·화면 공유 없이 기본 음성 회의를 진행할 수 있다.
- 정기 초안이 출처 링크와 함께 허용 audience 안에서만 생성된다.
- WF-08 전에는 자동 교차 게시 옵션이 존재하지 않는다.
- WF-08 후 자동 게시를 활성화하려면 승인 상태 전이 E2E와 source/target audience 검사가 모두 통과한다.
- 자동화 실패가 조용히 누락되지 않고 문서화된 사용자 가시 위치에서 확인된다.
- 자동화를 끄면 더 이상 요약이나 에이전트 호출이 발생하지 않는다.

### Phase 6 — 품질, 보안, 패키징

목표: 내부 파일럿이 가능한 SchoolX 2.0 설치본을 만든다.

작업:

## 10. upstream 동기화 전략

- `upstream/main`을 정기적으로 fetch한다.
- 큰 기능 개발 전과 PR 병합 전에 upstream 변경을 반영한다.
- 제품 설정, 번역 카탈로그, SchoolX 템플릿을 독립 디렉터리에 유지한다.
- upstream에도 일반적으로 유용한 개선은 제품 이름 없이 별도 PR로 제안할 수 있다.
- SchoolX 고유 브랜딩과 기본 업무방은 `DevYonghunT/buzz`에만 유지한다.

### 반영 방식: merge (rebase 아님)

`upstream/main`을 SchoolX 브랜치로 가져올 때는 **merge**를 사용한다.

```bash
git fetch upstream && git merge upstream/main
```

rebase는 SchoolX 커밋을 새로 써서 SHA를 바꾸므로, 이미 push된 브랜치에서는
force push가 필요하다. 공개 fork에서 force push는 원격 역사를 덮어쓰고 이
문서와 `BASELINE.md`가 참조하는 SHA를 무효화한다. merge는 커밋을 보존하고
"언제 어디까지 받았는지"를 merge commit에 남기므로 기준선 추적과 맞는다.

rebase는 **아직 push하지 않은 로컬 작업 브랜치**를 정리할 때만 쓴다.

### 주기: 주 1회 + 각 세션 시작 전

upstream은 2026-07-22~24 이틀 동안 57커밋이 들어올 만큼 활발하다. 미룰수록
겹치는 파일이 누적되고 충돌 원인 추적이 어려워지므로 간격을 짧게 유지한다.
`IMPLEMENTATION_HANDOFF.md`의 각 세션은 시작 전에 fetch·merge를 먼저 한다.

### 충돌 해소 원칙

번역 카탈로그가 걸린 충돌은 한쪽을 고르는 문제가 아니다. upstream이 문구의
**의미**를 바꾼 경우 i18n 키 사용은 유지하되 카탈로그의 한·영 문구를 새
의미에 맞춘다. 키를 지우거나 `t()` 호출을 하드코딩 문자열로 되돌리지 않는다.

자동 병합된 파일도 검토 대상이다. 텍스트 충돌이 없다는 것은 git이 같은 줄을
건드리지 않았다는 뜻일 뿐이며, SchoolX 보안 불변식(관리형 에이전트의
membership 강제)이 걸린 relay 경로는 upstream이 새 조회 경로를 추가했는지
매번 확인한다.

**네임스페이스 충돌은 텍스트 충돌로 나타나지 않는다.** 2026-07-28 동기화에서
upstream과 SchoolX가 같은 마이그레이션 번호(0025)로 서로 다른 파일을 추가했고,
git은 다른 파일이라 충돌 없이 병합했으며 빌드도 통과했다. 매 동기화 후 다음을
확인한다.

- `ls migrations/` — 같은 4자리 접두사가 둘 이상인지. SchoolX는 `9001+`를 쓴다.
- 새 이벤트 kind 정수가 `buzz-core/src/kind.rs`에서 겹치는지.
- 제품 식별자(번들 ID, 딥링크 스킴, nest, 키체인)를 upstream이 새 경로에서
  하드코딩했는지. `PRODUCT_IDENTITY.md` §3의 표가 대상 목록이다.

권장 브랜치 흐름:

```text
block/buzz:main
       │
       ▼
DevYonghunT/buzz:main
       │
       ├── codex/schoolx-2-foundation
       ├── codex/schoolx-2-security-contract
       ├── codex/schoolx-2-i18n
       ├── codex/schoolx-2-branding
       ├── codex/schoolx-2-workspace-template
       └── codex/schoolx-2-agent-operations
```

가능성이 검증된 뒤 `School-X520/schoolx-2.0`으로 옮길 때는 전체 역사를 다시 포크하기보다, 검증된 커밋과 제품 설정을 기준으로 저장소 소유권과 배포 설정을 정리한다.

## 11. 첫 번째 구현 묶음

현재 `a3e1ca4f`에서 2번의 foundation 일부가 먼저 구현됐지만, 다음
작업은 아래 의존성 순서를 따른다.

1. 원본 parent와 현재 snapshot의 같은 빌드·테스트 기준선을 `BASELINE.md`에 기록한다.
2. 사람/open 의미와 NIP-OA 에이전트의 명시적 멤버십, 직접 CLI 접근,
   source audience 교집합, WF-08 부재를 보안 계약과 E2E 명세로 고정한다.
3. 제품 설정 계층과 bundle ID, 데이터 디렉터리, 딥링크 호환성 결정을 먼저 완료한다.
4. 기존 i18n foundation의 fresh-install, 양방향 전환, fallback, typed-key 테스트를 보강한다.
5. 로그인, 앱 셸, 채널 목록, 메시지 작성 화면을 번역하고 한글 IME·검색을 검증한다.
6. versioned catalog와 provenance를 만들고 메인 회의방·기획방 private 채널만 agent 없이 적용한다.
7. preflight, 재적용, rename, 동명 충돌, 부분 실패 재시도 E2E를 통과한다.
8. 그 뒤 기획 에이전트와 코디네이터를 stable item key로 선택 배치하고 직접 CLI 권한 경계를 검증한다.
9. 기획 안건 → 같은 채널의 출처 포함 AI 초안 → 사용자 검토 → 결정 캔버스 수동 반영 → 회의방 접근 제어 링크 공유를 E2E로 검증한다.
10. 최소 preset과 보안 지표가 통과한 뒤에만 나머지 업무방으로 확장한다.

이 묶음은 “별도 기능 개발 없이 Buzz의 기존 구성 요소로 SchoolX 업무를
운영할 수 있는가”뿐 아니라 “그 구성이 같은 자격증명의 다른 도구 경로와
재적용 실패에서도 권한과 데이터를 보존하는가”를 함께 검증한다.

## 12. 후속 기능 결정 게이트

파일럿 이후에도 SchoolX 전용 기능은 바로 개발하지 않는다. 다음 증거가 있을 때만 별도 설계 단계로 이동한다.

| 후보 기능 | 개발을 검토할 조건 | 먼저 시도할 Buzz 방식 |
|---|---|---|
| 구조화된 의사결정 | 캔버스와 포럼만으로 결정 검색·상태 확인이 반복적으로 실패 | 결정 캔버스 템플릿과 태그 운영 개선 |
| 구조화된 태스크 | 담당자, 기한, 완료 여부 관리가 알림·체크리스트로 해결되지 않음 | 워크플로와 캔버스 체크리스트 개선 |
| 공유·가져오기 모델 | 링크 공유만으로 필요한 권한과 맥락을 제공할 수 없음 | 링크 미리보기와 출처 메타데이터 개선 |
| 검토형 도메인 메모리 | 검증된 캔버스 검색으로도 반복 업무의 정확도가 부족 | 캔버스 구조와 에이전트 검색 프롬프트 개선 |
| 파일 버전·세부 ACL | 채널 권한과 새 첨부 방식으로 규정 준수가 불가능 | 파일 운영 규칙 또는 외부 저장소 연계 검토 |
| Google 인증 | 파일럿 조직에서 계정 배포가 실제 도입 장애로 확인 | Buzz 신원에 조직 계정을 연결하는 방식 검토 |
| 영상·외부 회의 연동 | 음성 Huddle이 필수 회의 요구를 충족하지 못함 | 카메라·화면 공유 필요 비율을 측정하고 한 방식만 우선 검토 |
| 중앙 관리자 대시보드 | Buzz 관리 기능으로 반복 관리 업무를 처리할 수 없음 | 채널 역할과 감사 로그 운영 개선 |

기능 확장의 공통 승인 조건:

- 동일 문제가 여러 사용자와 여러 업무방에서 반복된다.
- 운영 교육이나 템플릿 개선으로 해결되지 않는다.
- 기존 Buzz 이벤트와 권한 모델을 유지할 수 있다.
- 새 기능의 보안·유지보수 비용보다 사용자 효과가 크다.
- 구현 전 성공 지표와 제거 가능한 기존 우회 절차가 정의되어 있다.

### 파일럿 측정 계약

보안과 idempotency는 사용자 만족도와 교환하지 않는 hard gate다. 사용성
비율은 최소 2주, 참여자 5명 이상, 해당 시나리오 20회 이상을 모은 뒤
판단한다. 표본이 부족하면 성공으로 간주하지 않고 `관찰 연장`으로 표시한다.

| 지표 | 계산 | 파일럿 기준 |
|---|---|---|
| private 접근 위반 | 권한 매트릭스 자동 테스트와 보고된 실제 위반 수 | 자동 테스트 100% 통과, 실제 위반 0건 |
| audience 초과 요약 | target audience가 source 교집합을 벗어난 생성·게시 수 | 0건 |
| 출처 완전성 | source가 필요한 AI 초안 중 접근 가능한 원본 링크가 모두 있는 비율 | 100%, 누락 0건 |
| 원본 이동 성공 | 권한이 있는 사용자의 원본 링크 열기 성공 / 시도 | 95% 이상 |
| template 재적용 | 재적용·부분 실패 matrix에서 예상 channel/agent 수와 일치한 비율 | 100%, 중복 0건 |

### 파일럿 개인정보 원칙

- 측정은 파일럿 참가자의 명시적 opt-in 후 시작하고 설정에서 중단할 수 있게 한다.
- 메시지·요약·canvas·파일 본문, 채널 이름, Nostr pubkey, event ID, 파일명은 수집하지 않는다.
- 링크 성공, 오류 종류, 단계 완료 여부는 장치 내 집계값 또는 임의 pilot participant ID의 최소 이벤트로만 기록한다.
- 원본 접근 위반과 보안 사고 조사를 위해 내용이 필요하면 자동 telemetry가 아니라 별도 동의와 사고 절차를 사용한다.
- 원시 파일럿 이벤트의 기본 보존 기간은 30일, 집계 결과는 90일로 제한하고 접근자는 지정된 파일럿 운영자만으로 한다.
- 참가자별 데이터 조회·삭제 방법과 수집 서버, 저장 위치, 제3자 전송 여부를 파일럿 시작 전에 문서화한다.
- opt-out 사용자도 핵심 기능을 동일하게 사용할 수 있어야 하며, 표본 부족은 telemetry 강제가 아니라 파일럿 연장으로 해결한다.
