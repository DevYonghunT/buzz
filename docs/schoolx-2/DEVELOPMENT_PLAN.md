# SchoolX 2.0 개발 계획

## 1. 목표

SchoolX 2.0은 Buzz를 기반으로 다음 목표를 달성한다.

- Buzz가 이미 제공하는 협업 기능을 최대한 그대로 사용한다.
- 기존 SchoolX의 업무방 구조와 에이전트 운영 방식을 Buzz의 선택형 채널 템플릿과 권한 제한형 에이전트로 재구성한다.
- 사용자 화면은 한국어를 기본으로 제공하되 영어 폴백을 유지한다.
- Buzz에 없는 SchoolX 전용 기능은 첫 버전에 새로 만들지 않는다.
- upstream `block/buzz`의 개선 사항을 계속 받아올 수 있도록 변경 범위를 얇게 유지한다.

SchoolX 2.0의 제품 정의는 새로운 협업 엔진이 아니라 **한국어 교육·연구 조직을 위한 Buzz 운영 패키지**다. 핵심 가치는 한국어 업무 환경, 목적별 워크스페이스 템플릿, 출처가 명확한 협업 에이전트에서 만든다.

## 2. 제품 원칙

### 2.1 Buzz 네이티브 우선

기능 요구가 생기면 아래 순서로 해결한다.

1. Buzz의 기존 기능을 설정이나 템플릿으로 조합한다.
2. 기존 Buzz 기능에 작은 확장 포인트를 추가한다.
3. 그래도 해결되지 않는 경우에만 SchoolX 전용 기능을 별도 백로그로 검토한다.

### 2.2 프로토콜과 데이터 호환성 유지

- 채널, 메시지, 멤버십은 Buzz가 사용하는 Nostr 이벤트 구조를 유지한다.
- 별도의 SchoolX 전용 HTTP API나 데이터베이스 테이블을 우선 도입하지 않는다.
- 사용자 콘텐츠는 SchoolX 전용 포맷으로 잠그지 않는다.
- CLI와 에이전트가 기존 Buzz 채널에 동일하게 접근할 수 있어야 한다.

### 2.3 제품 변경과 upstream 변경 분리

- 제품명, 아이콘, 기본 언어, 초기 템플릿은 SchoolX 설정 계층에 모은다.
- Buzz 핵심 로직을 직접 복제하거나 대규모로 수정하지 않는다.
- upstream 동기화 시 충돌이 잦은 파일은 가능한 한 래퍼나 설정 파일로 분리한다.

### 2.4 복제 대신 출처가 있는 공유

- 다른 업무방에 내용을 복사하거나 가져오기보다 원본 메시지와 스레드를 링크한다.
- 공유되는 요약에는 원본 채널, 작성자, 작성 시각, 원본 링크를 포함한다.
- 원본을 열 권한이 없는 사용자에게 비공개 내용을 요약해 노출하지 않는다.
- 회의방은 다른 업무방의 사본 저장소가 아니라, 출처 링크를 중심으로 논의하고 결정하는 공간으로 사용한다.

### 2.5 자동 영구 기억 대신 검증된 지식

정보는 다음 세 단계로 다룬다.

1. **대화**: 검색 가능한 원본이지만 공식 지식은 아니다.
2. **AI 요약**: 출처를 포함한 임시 결과이며 언제든 원본과 대조할 수 있다.
3. **검증된 캔버스**: 사람이 확인해 공식 지식으로 승격한 내용이다.

AI가 모든 대화를 자동으로 영구 기억하게 하지 않는다. 장기적으로 재사용할 지식은 사용자의 명시적 승격을 거쳐 캔버스에 기록한다.

### 2.6 최소 권한과 요청 기반 자동화

- 코디네이터는 모든 채널을 기본 감시하지 않는다.
- 코디네이터와 업무방 에이전트는 초대된 채널만 읽고 쓴다.
- 다른 채널로 내용을 게시하거나 외부 도구를 실행하는 작업은 사용자의 요청 또는 확인이 있어야 한다.
- 정기 요약은 관리자가 활성화한 채널과 시간 범위에 대해서만 실행한다.
- 결과에는 근거 링크와 실패 상태가 반드시 표시되어야 한다.

### 2.7 고정 구조 대신 선택형 시작 템플릿

- 기존 SchoolX 업무방은 필수 데이터 구조가 아니라 선택 가능한 시작 템플릿으로 제공한다.
- 관리자는 필요한 업무방과 에이전트만 선택할 수 있다.
- 템플릿 적용 후에도 일반 Buzz 채널처럼 이름, 멤버, 에이전트, 운영 방식을 변경할 수 있다.
- 사용하지 않는 업무방과 에이전트를 자동으로 생성하지 않는다.

### 2.8 목표 구조

```text
SchoolX 제품 계층
├── 브랜드와 배포 설정
├── 한국어·영어 번역 카탈로그
├── 교육·연구 조직용 워크스페이스 템플릿
├── 페르소나와 에이전트 운영 정책
└── 캔버스·포럼·워크플로 운영 예제
              │
              ▼
Buzz 애플리케이션 계층
├── 채널·멤버십·메시지·검색
├── 에이전트·페르소나·팀
├── 캔버스·포럼·알림·워크플로
└── Huddle·파일·감사
              │
              ▼
Nostr 이벤트와 Buzz 인프라
```

SchoolX 계층은 Buzz의 공개된 기능과 일반화된 확장 지점을 사용한다. Buzz 핵심 계층에는 SchoolX 업무방 이름이나 전용 비즈니스 규칙을 넣지 않으며, 핵심 변경이 필요하면 다른 Buzz 배포에서도 사용할 수 있는 일반 기능으로 구현한다.

## 3. 1차 버전 범위

### 포함

- SchoolX 2.0 브랜딩
- 데스크톱 앱 핵심 화면 한국어화
- 한국어 입력기(IME), 검색, 날짜 및 시간 표시 검증
- 필요한 SchoolX 업무방을 선택해 생성하는 워크스페이스 템플릿
- 업무방별 재사용 가능 페르소나와 선택형 관리형 AI 에이전트
- 허용된 채널만 요청 기반으로 종합하는 회의방 코디네이터
- 메시지, 스레드, 반응, 검색, 파일, 캔버스, 포럼, 알림 기능
- Buzz Huddle을 이용한 실시간 회의
- Buzz 워크플로를 이용한 출처 기반 반복 요약
- 채널 권한과 멤버십을 이용한 기본 접근 제어
- 데스크톱 패키징과 내부 시험 배포

### 제외

- 기존 SchoolX 데이터의 자동 마이그레이션
- `shared_items`, `meeting_imports`와 같은 구조화된 공유·가져오기 모델
- 별도 의사결정 테이블과 태스크 관리 데이터 모델
- 검토 대기열이 있는 업무방별 도메인 메모리
- 파일 버전 관리와 SchoolX 전용 파일 ACL
- Google OAuth와 이메일 허용 목록
- Google Meet 및 Zoom 연동
- 기존 SchoolX와 완전히 동일한 관리자 대시보드
- 모바일과 웹의 전체 한국어화

제외 기능은 삭제하는 것이 아니라, 실제 사용 과정에서 Buzz 네이티브 기능만으로 부족한지 확인한 뒤 후속 버전에서 판단한다. “익숙했던 기능”이라는 이유만으로 복원하지 않고, 파일럿에서 반복적으로 해결되지 않은 사용자 문제가 확인된 경우에만 구현 후보가 된다.

## 4. 한글화 가능성 및 전략

### 4.1 조사 결과

한글화는 가능하다. 현재 Buzz에는 앱 전체를 위한 다국어 프레임워크가 없고, 데스크톱·웹·모바일 화면에 영어 문구가 직접 작성되어 있다.

- 데스크톱은 React/TypeScript이므로 런타임 언어 전환과 번역 카탈로그를 추가할 수 있다.
- 메시지 입력기는 웹 편집기 기반이므로 한글 입력이 가능하지만, 조합 중 Enter 처리와 멘션·자동완성은 별도 회귀 테스트가 필요하다.
- 날짜 표시는 상당 부분 운영체제 로케일을 따르지만, 표시 형식을 `ko-KR` 기준으로 통일해야 한다.
- 현재 기본 글꼴인 Inter에는 한글 글리프가 충분하지 않아 시스템 글꼴로 폴백된다. 명시적인 한국어 시스템 글꼴 스택이 필요하다.
- 모바일에는 `intl` 패키지가 있지만 Flutter 로컬라이제이션 설정은 아직 없다.

### 4.2 적용 원칙

- 1차 대상은 데스크톱 앱으로 제한한다.
- 기본 언어는 한국어, 폴백 언어는 영어로 한다.
- 사용자가 설정에서 한국어와 영어를 바꿀 수 있게 한다.
- 프로토콜 이름, CLI 명령, 이벤트 kind, 로그 필드는 번역하지 않는다.
- 사용자에게 노출되는 Rust/Tauri 오류는 점진적으로 안정된 오류 코드에 매핑해 번역한다.
- 개발 문서와 코드 식별자는 영어를 유지한다.

### 4.3 권장 구현

데스크톱에 `i18next`와 `react-i18next`를 도입하고 기능별 namespace로 번역 파일을 나눈다.

예상 구조:

```text
desktop/src/shared/i18n/
├── index.ts
├── locale.ts
└── locales/
    ├── en/
    │   ├── common.json
    │   ├── channels.json
    │   ├── agents.json
    │   └── settings.json
    └── ko/
        ├── common.json
        ├── channels.json
        ├── agents.json
        └── settings.json
```

번역은 한 번에 모든 파일을 바꾸지 않고 사용자 여정 순서로 진행한다.

1. 앱 셸, 로그인과 온보딩
2. 채널 생성·참여·멤버 관리
3. 메시지·스레드·검색·파일
4. 에이전트·페르소나·팀
5. 캔버스·포럼·알림
6. Huddle·워크플로
7. 설정·오류·빈 상태

### 4.4 한글화 완료 기준

- 새 사용자가 영어 화면 없이 로그인하고 SchoolX 워크스페이스에 들어갈 수 있다.
- 채널 생성부터 메시지, 파일 공유, 에이전트 호출까지 핵심 흐름이 한국어로 표시된다.
- 한글 자모가 중복되거나 분리되지 않는다.
- 조합 중 Enter가 메시지를 잘못 전송하지 않는다.
- 한글 채널명, 한글 파일명, 한글 검색어가 정상 동작한다.
- 번역 키가 누락되면 앱이 깨지지 않고 영어가 표시된다.
- `ko-KR`과 영어 환경에서 레이아웃이 잘리거나 겹치지 않는다.

## 5. SchoolX 기능을 Buzz로 구성하는 방법

| SchoolX 사용 목적 | SchoolX 2.0에서 사용할 Buzz 기능 | 1차 구현 방식 |
|---|---|---|
| 부서·업무방 | NIP-29 채널과 멤버십 | 관리자가 선택한 채널만 워크스페이스 템플릿으로 생성 |
| 업무방 전문 AI | 관리형 에이전트, 페르소나, 팀 | 페르소나는 제공하되 자주 쓰는 방만 관리형 에이전트를 활성화 |
| 메인 회의방 | 채널, 스레드, Huddle | 전체 멤버가 참여하는 회의 채널과 실시간 Huddle 사용 |
| 총괄 조정 AI | 제한된 채널 멤버십을 가진 관리형 에이전트 | 허용된 채널만 요청 시 검색·요약하고 자동 교차 게시 금지 |
| 회의 결과 정리 | 스레드 요약, 채널 요약, 캔버스 | 출처가 있는 임시 요약을 사람이 확인한 뒤 캔버스에 승격 |
| 부서 간 공유 | 메시지 링크, 멘션, 캔버스, 포럼 | 내용을 복제하지 않고 원본 메시지 링크와 요약을 공유 |
| 의사결정 | 포럼 글, 스레드, 반응, 캔버스 | 포럼에서 합의한 뒤 검증된 결과만 결정 캔버스에 기록 |
| 할 일 | 알림, 워크플로, 캔버스 체크리스트 | 담당자 멘션, 기한 알림, 반복 워크플로 사용 |
| 자료 공유 | Buzz 파일 업로드와 미디어 | 채널이나 스레드에 파일을 올려 대화 맥락과 결합 |
| 지식 축적 | 검색, 출처 기반 요약, 캔버스 | 대화 → AI 요약 → 사람이 검증한 캔버스의 3단계로 관리 |
| 정기 보고 | 워크플로 YAML과 에이전트 | 활성화한 채널만 요약하고 출처 링크와 함께 회의방에 게시 |
| 접근 권한 | 채널 역할과 멤버십 | 공개 범위와 채널 멤버를 기준으로 제한 |
| 화상 회의 | Buzz Huddle | Meet/Zoom 대신 내장 Huddle 우선 사용 |
| 변경 이력 | 이벤트 로그와 감사 체인 | Buzz의 이벤트 및 감사 기능을 그대로 사용 |

## 6. 기본 워크스페이스 설계

기존 SchoolX의 활성 업무방을 선택형 템플릿으로 제공한다. 설치 시 채널이나 에이전트를 강제로 생성하지 않고, 관리자가 “SchoolX 기본 워크스페이스” 미리보기에서 필요한 항목만 선택한다.

| 키 | 표시 이름 | 기본 역할 | 제공 페르소나 | 초기 활성화 |
|---|---|---|---|---|
| `meeting` | 메인 회의방 | 전사 회의, 종합 보고, Huddle | SchoolX 코디네이터 | 파일럿에서 선택 |
| `finance` | 재무 | 예산, 지출, 정산 | 재무 담당 | 비활성 |
| `planning` | 기획 | 사업 기획, 일정, 제안 | 기획 담당 | 파일럿에서 선택 |
| `external` | 대외협력 | 기관 협력, 공문, 대외 일정 | 대외협력 담당 | 비활성 |
| `development` | 개발 | 제품 개발, 기술 검토 | 개발 담당 | 비활성 |
| `research` | 연구 | 조사, 자료 분석, 연구 기록 | 연구 담당 | 비활성 |
| `promotion` | 홍보 | 콘텐츠, 보도, 홍보 일정 | 홍보 담당 | 비활성 |
| `province_research` | 경기도교육연구회 | 지역 연구회 협업 | 연구회 담당 | 비활성 |
| `science_museum` | 과학관 AI교육 연구회 | AI 교육 공동 연구 | AI교육 연구 담당 | 비활성 |
| `gwangju_hanam_research` | 광주하남교육연구회 | 지역 연구회 협업 | 연구회 담당 | 비활성 |

비활성 상태였던 `city_research`는 기본 템플릿에서 제외한다.

### 채널 기본 구성

각 업무방 템플릿에는 다음 항목을 포함한다.

- 한글 채널 이름과 설명
- 채널의 목적과 운영 규칙을 담은 시작 캔버스
- 업무방에 맞는 에이전트 페르소나
- 관리형 에이전트 활성화 여부 선택
- 반복 업무를 위한 선택형 워크플로 예제
- 결정 기록, 주간 요약, 할 일 기록용 캔버스 섹션
- 새 멤버가 따라 할 수 있는 한국어 시작 안내

### 에이전트 권한 원칙

- 업무방 에이전트는 기본적으로 해당 채널만 읽고 쓴다.
- 코디네이터는 사용자가 명시적으로 허용한 업무방에만 참여한다.
- 코디네이터는 호출 또는 활성화된 일정이 없으면 채널을 자동 요약하지 않는다.
- 비공개 채널의 정보를 다른 채널에 자동 복사하지 않는다.
- 채널 간 요약은 출처 메시지 링크와 대상 채널을 명시한다.
- 에이전트 메모리는 공식 지식으로 간주하지 않으며, 캔버스 승격은 사람이 결정한다.
- 외부 도구 호출이나 게시 전 승인 기능이 필요한 업무는 1차 버전에서 자동 실행하지 않는다.

## 7. 단계별 개발 계획

### Phase 0 — 기준선과 개발 운영

목표: 원본 Buzz가 정상 동작하는 기준선을 만들고 upstream 추적 방식을 고정한다.

작업:

- `origin`은 `DevYonghunT/buzz`, `upstream`은 `block/buzz`로 유지
- SchoolX 개발 브랜치는 `codex/schoolx-2-foundation`에서 시작
- 데스크톱 개발 빌드, 테스트, 린트의 현재 상태 기록
- SchoolX 변경 사항의 디렉터리와 네이밍 규칙 확정
- Apache-2.0 원문, NOTICE, 서드파티 라이선스 보존 확인
- upstream 반영 절차 문서화

완료 기준:

- 수정 전 Buzz 데스크톱을 로컬에서 실행할 수 있다.
- 현재 실패하는 테스트와 새 변경으로 발생한 실패를 구분할 수 있다.
- upstream fetch와 병합을 반복할 수 있다.

### Phase 1 — 한글화 기반과 브랜딩

목표: 제품의 첫 사용자 여정을 한국어 SchoolX 앱으로 만든다.

작업:

- 데스크톱 번역 초기화 모듈과 한국어·영어 카탈로그 추가
- 운영체제 언어 감지, 사용자 언어 설정, 영어 폴백 구현
- 앱 셸, 로그인, 온보딩, 채널 목록, 메시지 화면 우선 번역
- 한국어 시스템 글꼴 스택 적용
- 날짜·시간·숫자 표시를 현재 언어에 맞게 통일
- 제품명, 아이콘, 앱 식별자, 딥링크를 SchoolX 설정으로 분리
- “Buzz”가 프로토콜이나 기술 설명인지 제품명인지 구분해 번역

결정이 필요한 값:

- 최종 제품 표시명
- macOS/Windows/Linux 앱 식별자
- 딥링크 스킴
- 아이콘과 색상
- 업데이트 서버와 배포 서명 주체

완료 기준:

- 한국어 환경에서 설치, 실행, 로그인, 채널 입장, 메시지 전송이 가능하다.
- 영어를 선택하면 기존 영어 UI로 돌아간다.
- 한글 IME 핵심 회귀 테스트가 통과한다.
- upstream 변경과 제품 브랜딩 변경이 가능한 한 분리되어 있다.

### Phase 2 — SchoolX 워크스페이스 템플릿

목표: 빈 Buzz 설치를 SchoolX 업무 공간으로 빠르게 구성한다.

작업:

- SchoolX 선택형 채널 템플릿 정의
- 활성 업무방 10개와 설명, 시작 캔버스를 선택 항목으로 작성
- 업무방별 재사용 페르소나와 선택형 관리형 에이전트 템플릿 작성
- 메인 회의방과 기획방만 선택된 최소 파일럿 프리셋 제공
- 템플릿 미리보기와 선택 적용 흐름 추가
- 기존 채널과 이름이 충돌할 때 중복 생성을 막는 규칙 추가
- 템플릿 적용 결과와 부분 실패를 사용자에게 표시

완료 기준:

- 관리자가 필요한 업무방, 페르소나, 관리형 에이전트를 각각 선택할 수 있다.
- 선택하지 않은 업무방과 에이전트는 생성되지 않는다.
- 재적용해도 채널과 에이전트가 무제한 중복 생성되지 않는다.
- 활성화한 업무방에서만 해당 관리형 에이전트를 호출할 수 있다.
- 채널을 추가하거나 제외해도 Buzz의 일반 채널과 동일하게 동작한다.

### Phase 3 — 네이티브 협업 흐름 완성

목표: SchoolX의 일상 업무를 새 데이터 모델 없이 Buzz 안에서 수행한다.

대표 시나리오:

1. 기획방에서 안건을 포럼 글로 작성한다.
2. 관련 자료를 파일로 첨부하고 담당자를 멘션한다.
3. 토론은 스레드로 유지한다.
4. 에이전트가 출처 링크를 포함한 임시 요약을 만든다.
5. 사람이 확인한 합의 결과만 결정 기록 캔버스에 승격한다.
6. 캔버스에는 원본 안건과 토론 스레드 링크를 유지한다.
7. 필요한 후속 작업은 알림이나 워크플로로 등록한다.
8. 원본 메시지 링크와 검증된 요약을 메인 회의방에 공유한다.

작업:

- 결정 기록, 할 일, 주간 보고용 캔버스 템플릿 작성
- 포럼·스레드·반응을 이용한 합의 운영 규칙 정의
- 채널 간 링크 공유 시 원본 출처가 보이는지 검증
- AI 요약을 임시 상태로 표시하고 캔버스 승격은 사용자가 수행
- 캔버스 기록에 원본 메시지와 회의 스레드 링크를 유지
- 한글 파일명 업로드·다운로드·검색 검증
- 알림과 반복 워크플로의 한국어 UX 정리

완료 기준:

- 회의, 결정, 후속 작업, 자료 공유가 Buzz 네이티브 기능만으로 이어진다.
- 관리자가 별도 DB 화면 없이 업무 진행 상황을 확인할 수 있다.
- 출처 채널과 원본 메시지를 잃지 않고 부서 간 공유가 가능하다.
- AI 요약과 사람이 검증한 공식 기록이 화면과 운영 규칙에서 구분된다.
- 비공개 원본을 열 수 없는 사용자에게 해당 내용의 요약도 노출되지 않는다.

### Phase 4 — 에이전트 운영

목표: 필요한 업무방에만 전문 에이전트를 활성화하고, 최소 권한 코디네이터를 안전하게 운영한다.

작업:

- 업무방별 시스템 프롬프트, 역할, 금지 사항 정의
- 페르소나 호출과 상주 관리형 에이전트의 사용 기준 정의
- 관리형 에이전트는 템플릿에서 기본 비활성 상태로 제공
- 에이전트가 사용하는 Buzz CLI 도구와 채널 범위 검증
- 메인 회의방 코디네이터를 관리자가 허용한 채널에만 멤버로 추가
- 사용자 호출 또는 활성화된 일정이 있을 때만 코디네이터가 보고서를 생성
- 채널·스레드 요약과 검색을 조합한 보고 흐름 작성
- 요약에 출처 링크를 포함하도록 프롬프트와 출력 포맷 통일
- 채널 간 게시 전 대상, 포함 내용, 공개 범위를 확인하는 흐름 정의
- 실패, 타임아웃, 권한 부족 시 사용자에게 보이는 상태 정리

완료 기준:

- 업무방 에이전트가 다른 비공개 업무방을 임의로 읽지 못한다.
- 비활성 에이전트가 백그라운드에서 호출되거나 비용을 발생시키지 않는다.
- 코디네이터의 보고에서 근거 메시지로 이동할 수 있다.
- 코디네이터가 멤버가 아닌 채널의 제목, 메시지, 요약을 얻지 못한다.
- 자동 교차 게시 없이도 사용자가 보고서를 검토하고 공유할 수 있다.
- 에이전트가 답을 만들지 못할 때 추측 대신 실패 상태를 알린다.
- 에이전트 동작이 일반 Buzz 채널 멤버십 규칙을 우회하지 않는다.

### Phase 5 — 회의와 자동화

목표: 외부 회의·자동화 제품 없이 Buzz 내장 기능의 실사용 가능성을 검증한다.

작업:

- 메인 회의방에서 Huddle 생성·참여·종료 흐름 한국어화
- 회의 스레드 요약을 캔버스에 반영하는 운영 흐름 작성
- 관리자가 선택한 채널을 대상으로 일간·주간 업무 요약 워크플로 예제 추가
- 특정 채널의 새 안건 링크를 회의방에 알리는 워크플로 검증
- 요약 게시 전 사용자 확인이 필요한 모드와 자동 게시 모드를 구분
- 외부 실행이나 중요 게시가 필요한 자동화는 사용자 확인 단계 유지

완료 기준:

- 팀이 Meet/Zoom 없이 기본 화상·음성 회의를 진행할 수 있다.
- 정기 요약이 출처 링크와 함께 허용된 채널에만 게시된다.
- 자동화 실패가 조용히 누락되지 않고 채널에서 확인된다.
- 자동화를 끄면 더 이상 요약이나 에이전트 호출이 발생하지 않는다.

### Phase 6 — 품질, 보안, 패키징

목표: 내부 파일럿이 가능한 SchoolX 2.0 설치본을 만든다.

작업:

- 한국어·영어 핵심 E2E 시나리오 작성
- 권한, 비공개 채널, 에이전트 접근 범위 보안 점검
- macOS 우선 패키징 후 Windows와 Linux 확인
- 앱 식별자, 딥링크, 데이터 디렉터리 충돌 검증
- 오픈소스 고지와 서드파티 라이선스 화면 검증
- 오류 수집과 개인정보 처리 범위 문서화
- 소규모 사용자 파일럿과 사용성 피드백 수집

완료 기준:

- 기존 Buzz 설치와 SchoolX 설치가 서로의 데이터를 덮어쓰지 않는다.
- 설치·업데이트·제거 흐름이 검증된다.
- 핵심 업무 시나리오와 권한 테스트가 통과한다.
- Apache-2.0 고지 의무를 지키면서 상업 배포할 수 있다.

## 9. 개발 및 검증 규칙

각 단계는 작은 PR 단위로 나눈다.

1. 기반 구조와 테스트
2. 번역 또는 템플릿 데이터
3. UI 연결
4. E2E 검증
5. 문서 갱신

필수 검증:

- TypeScript 타입 검사
- 데스크톱 단위 테스트
- Rust 포맷과 테스트
- 린트
- 한국어 IME 수동 및 자동 회귀 검사
- 한국어와 영어 핵심 사용자 여정 E2E
- 비공개 채널과 에이전트 권한 경계 검사

번역 PR은 기능 변경과 섞지 않는다. 브랜딩 변경도 가능하면 번역 변경과 별도 커밋으로 유지한다.

## 10. upstream 동기화 전략

- `upstream/main`을 정기적으로 fetch한다.
- 큰 기능 개발 전과 PR 병합 전에 upstream 변경을 반영한다.
- 제품 설정, 번역 카탈로그, SchoolX 템플릿을 독립 디렉터리에 유지한다.
- upstream에도 일반적으로 유용한 개선은 제품 이름 없이 별도 PR로 제안할 수 있다.
- SchoolX 고유 브랜딩과 기본 업무방은 `DevYonghunT/buzz`에만 유지한다.

권장 브랜치 흐름:

```text
block/buzz:main
       │
       ▼
DevYonghunT/buzz:main
```

## 11. 첫 번째 구현 묶음

첫 구현은 다음 순서가 가장 안전하다.

1. 현재 Buzz 데스크톱의 빌드·테스트 기준선을 기록한다.
2. 다국어 초기화와 한국어·영어 전환만 추가한다.
3. 로그인, 앱 셸, 채널 목록, 메시지 작성 화면을 번역한다.
4. 한글 IME와 검색을 검증한다.
5. 제품 설정 계층을 만들고 SchoolX 표시명을 적용한다.
6. 메인 회의방과 기획방 두 개만 포함한 시험 템플릿을 만든다.
7. 기획 에이전트는 기획방에, 코디네이터는 사용자가 허용한 메인 회의방과 기획방에만 배치한다.
8. 기획 안건 작성 → 출처 포함 AI 요약 → 사용자 검토 → 회의방 링크 공유 → 결정 캔버스 승격 시나리오를 E2E로 검증한다.
9. 시험 템플릿이 안정되면 나머지 업무방으로 확장한다.

이 묶음이 통과하면 SchoolX 2.0의 핵심 가설인 “별도 기능 개발 없이 Buzz의 기존 구성 요소로 SchoolX 업무를 운영할 수 있는가”를 가장 적은 변경으로 검증할 수 있다.

## 12. 후속 기능 결정 게이트

파일럿 이후에도 SchoolX 전용 기능은 바로 개발하지 않는다. 다음 증거가 있을 때만 별도 설계 단계로 이동한다.

| 후보 기능 | 개발을 검토할 조건 | 먼저 시도할 Buzz 방식 |
|---|---|---|
| 구조화된 의사결정 | 캔버스와 포럼만으로 결정 검색·상태 확인이 반복적으로 실패 | 결정 캔버스 템플릿과 태그 운영 개선 |
| 구조화된 태스크 | 담당자, 기한, 완료 여부 관리가 알림·체크리스트로 해결되지 않음 | 워크플로와 캔버스 체크리스트 개선 |
| 공유·가져오기 모델 | 링크 공유만으로 필요한 권한과 맥락을 제공할 수 없음 | 링크 미리보기와 출처 메타데이터 개선 |
| 검토형 도메인 메모리 | 검증된 캔버스 검색으로도 반복 업무의 정확도가 부족 | 캔버스 구조와 에이전트 검색 프롬프트 개선 |
| 파일 버전·세부 ACL | 채널 권한과 새 첨부 방식으로 규정 준수가 불가능 | 파일 운영 규칙 또는 외부 저장소 연계 검토 |
| Google 인증 | 파일럿 조직에서 계정 배포가 실제 도입 장애로 확인 | Buzz 신원에 조직 계정을 연결하는 방식 검토 |
| Meet·Zoom 연동 | Huddle이 필수 회의 요구를 충족하지 못함 | 부족한 요구를 측정하고 한 공급자만 우선 검토 |
| 중앙 관리자 대시보드 | Buzz 관리 기능으로 반복 관리 업무를 처리할 수 없음 | 채널 역할과 감사 로그 운영 개선 |

기능 확장의 공통 승인 조건:

- 동일 문제가 여러 사용자와 여러 업무방에서 반복된다.
- 운영 교육이나 템플릿 개선으로 해결되지 않는다.
- 기존 Buzz 이벤트와 권한 모델을 유지할 수 있다.
- 새 기능의 보안·유지보수 비용보다 사용자 효과가 크다.
- 구현 전 성공 지표와 제거 가능한 기존 우회 절차가 정의되어 있다.

첫 파일럿에서는 다음 항목을 측정한다.

- 공유된 요약에서 원본으로 이동할 수 있는 비율
- AI 요약이 캔버스로 승격되기 전 사용자 수정 빈도
- 네이티브 알림·캔버스로 완료 가능한 후속 작업 비율
- 사용자가 실제 활성화한 업무방과 에이전트 수
- 코디네이터 보고서의 출처 누락과 권한 오류
- Huddle로 완료 가능한 내부 회의 비율
- 영어 화면 노출, 한글 입력 오류, 번역 누락 건수
